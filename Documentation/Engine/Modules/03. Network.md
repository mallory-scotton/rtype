# 🌐 Network

## Architecture Overview

The TKD Engine's network system is built on a **layered architecture** with clear separation of concerns, providing robust UDP-based networking for multiplayer games.

### Core Components

The network system consists of five primary components that work together:

#### 1. **FNetworkBase** (Abstract Base Class)

**Purpose**: Provides common UDP networking infrastructure for both client and server implementations.

**Libraries Used**:
- **ASIO**: Asynchronous UDP socket operations (`asio::io_context`, `asio::ip::udp::socket`)
- **FThread**: Engine's threading abstraction for dedicated network thread
- **Standard Libraries**: `<atomic>`, `<mutex>`, `<queue>`, `<unordered_map>`

**Key Features**:
- UDP socket management and lifecycle
- Packet routing via `FPacketManager`
- Network statistics tracking (`FNetworkStatistics`)
- Thread-safe packet queuing
- Abstract methods for derived classes to implement

**Role**: Foundation class that handles all low-level networking, allowing derived classes to focus on client/server-specific logic.

---

#### 2. **FNetworkServer** (Concrete Implementation)

**Purpose**: Server-side network management for multiplayer games, handling multiple client connections.

**Inherits From**: `FNetworkBase`

**Additional Dependencies**:
- `FConnectionInformation`: Tracks individual client connections
- `EventEmitter`: Event-driven architecture for connection state changes
- `FMutex`: Thread synchronization primitives
- `<chrono>`: Heartbeat and timeout timing

**Key Features**:
- Multi-client connection management
- Heartbeat system (5-second intervals)
- Automatic timeout detection (30 seconds)
- Sequential client ID assignment
- Snapshot buffering (circular buffer of 64 snapshots)
- Broadcasting and unicast packet sending

**Role**: Manages server-side networking, including client lifecycle, heartbeats, and world state synchronization.

---

#### 3. **FNetworkClient** (Concrete Implementation)

**Purpose**: Client-side network management for connecting to game servers.

**Inherits From**: `FNetworkBase`

**Additional Dependencies**:
- `IProperty`: Property serialization for snapshot application
- `EventEmitter`: Connection state event notifications
- `<optional>`: Optional connection state tracking

**Key Features**:
- Single server connection management
- Reconnection logic
- Snapshot application (full/delta modes)
- Actor state synchronization
- Client-side prediction support

**Role**: Manages client-side networking, handling server communication and applying world state updates.

---

#### 4. **FWorldInterface** (Thread-Safe World Access)

**Purpose**: Provides thread-safe access to the game world from network threads.

**Dependencies**:
- `FEngineInterface`: Access to engine subsystems
- `std::mutex`: Thread synchronization

**Key Pattern**: `WithWorld()` lambda function for thread-safe operations:
```cpp
FWorldInterface::WithWorld([](UWorld& world) {
    // Safely access world from network thread
    auto actors = world.GetActors();
});
```

**Usage**: Both `FNetworkServer` and `FNetworkClient` use this interface to safely access and modify the game world from their dedicated network threads, preventing race conditions and deadlocks.

**Role**: Critical bridge between network threads and the main game thread, ensuring data integrity.

---

#### 5. **FFragmentManager** (Singleton)

**Purpose**: Handles automatic fragmentation and reassembly of large packets.

**Library**: Self-contained, no external dependencies

**Used By**: Both server and client for packets exceeding 512 bytes

**Key Features**:
- Automatic packet fragmentation
- Reliable reassembly with retransmission
- Thread-safe operations
- Fragment acknowledgment system

**Role**: Transparent large packet handling, allowing the rest of the system to send packets of any size without concern for MTU limits.

---

## Library Ecosystem

The network system's dependency hierarchy:

```
FNetworkBase (Abstract)
├── ASIO Library
│   └── UDP async I/O, io_context, socket operations
├── FThread (Engine Threading)
│   └── Dedicated network thread management
├── FPacketManager (Packet Routing)
│   └── Routes incoming packets to registered handlers
├── FNetworkStatistics (Metrics)
│   └── Tracks bandwidth, packet counts, latency
└── Standard: atomic, mutex, queue, unordered_map
    └── Thread-safe data structures

FNetworkServer : FNetworkBase
├── FConnectionInformation (Client Tracking)
│   └── Per-client connection state and metadata
├── EventEmitter (Event System)
│   └── ServerStarted, ClientConnected, ClientDisconnected events
├── FMutex (Concurrency)
│   └── Thread synchronization for client map
├── chrono (Timing)
│   └── Heartbeat intervals and timeout detection
└── Snapshot Buffer (64 snapshots)
    └── Circular buffer for delta compression

FNetworkClient : FNetworkBase
├── IProperty (Serialization)
│   └── Property value updates from snapshots
├── EventEmitter (Events)
│   └── Connected, Disconnected, ConnectionFailed events
└── optional (Connection State)
    └── Optional server connection tracking

FWorldInterface (Thread-Safe World)
├── FEngineInterface (Subsystem Access)
│   └── Access to world subsystem
└── mutex (Thread Safety)
    └── Prevents concurrent world access

FFragmentManager (Singleton)
└── Self-contained fragmentation
    └── Fragment assembly, retransmission logic
```

## System Flow

### 1. Initialization Flow

```
Application Start
    ↓
FNetworkServer/FNetworkClient constructed with port
    ↓
Inherits FNetworkBase infrastructure
    ↓
ASIO io_context and UDP socket created
    ↓
FPacketManager initialized with default handlers
```

### 2. Start Flow

```
Start() called
    ↓
Socket binds to port
    ↓
Network thread spawned via FThread
    ↓
ASIO async_receive_from() started
    ↓
Server/Client emits "Started" event
```

### 3. Packet Reception Flow

```
UDP packet arrives
    ↓
ASIO callback on network thread
    ↓
Packet header parsed
    ↓
FFragmentManager checks if fragment
    ├── Yes: Reassemble fragments
    │   ├── Complete: Continue to routing
    │   └── Incomplete: Store and wait
    └── No: Continue to routing
        ↓
FPacketManager routes to registered handler
    ↓
Handler executes (may use FWorldInterface::WithWorld())
    ↓
Response packets queued if needed
```

### 4. Packet Transmission Flow

```
SendPacket() called
    ↓
Packet serialized via FBinaryWriter
    ↓
Size checked
    ├── > 512 bytes: FFragmentManager splits
    │   └── Multiple Fragment packets created
    └── ≤ 512 bytes: Single packet
        ↓
ASIO async_send_to() on network thread
    ↓
Statistics updated
```

### 5. Snapshot Synchronization Flow (Server → Client)

```
Server: TakeSnapshot() called (10 Hz)
    ↓
FWorldInterface::WithWorld() acquires lock
    ↓
World state serialized (actors, transforms, properties)
    ↓
Snapshot stored in circular buffer (index = snapshotID % 64)
    ↓
For each client:
    ├── Has acknowledged snapshot? 
    │   ├── Yes: Send Delta snapshot
    │   └── No: Send Full snapshot
    └── FFragmentManager handles if large
        ↓
Client receives snapshot
    ↓
Client: HandleSnapshotPacket()
    ↓
FWorldInterface::WithWorld() acquires lock
    ├── Full: Replace all actor states
    └── Delta: Apply only changes (modify/add/remove)
        ↓
Client sends SnapshotAck back to server
    ↓
Server stores client's last acknowledged snapshot
```

### 6. Thread-Safe World Access Pattern

```
Network Thread (Background)
    ↓
Needs to access/modify world
    ↓
FWorldInterface::WithWorld([](UWorld& world) {
    // Thread-safe world access
    world.SpawnActor<MyActor>();
    auto actors = world.GetActors();
});
    ↓
Lambda executes with exclusive world lock
    ↓
Mutex automatically released after lambda completes
    ↓
Main game thread can safely tick world
```

## Key Design Patterns

### 1. **Abstract Factory Pattern**
`FNetworkBase` defines the interface, while `FNetworkServer` and `FNetworkClient` provide concrete implementations with specialized behavior.

### 2. **Observer Pattern**
`EventEmitter` allows loose coupling between network events and game logic:
```cpp
server.On<Events::ClientConnected>([](const auto& event) {
    // React to client connection
});
```

### 3. **Command Pattern**
Packets implement `IPacket` interface with `Serialize()` and `Deserialize()`, encapsulating network commands.

### 4. **Singleton Pattern**
`FFragmentManager` uses singleton to provide global fragmentation services without coupling.

### 5. **Resource Acquisition Is Initialization (RAII)**
`FWorldInterface::WithWorld()` uses lambda scoping to automatically manage mutex lifetime.

## Thread Safety Guarantees

- **Network Thread**: Dedicated thread runs ASIO event loop, handles all socket I/O
- **Main Thread**: Game loop, world ticking, actor updates
- **Synchronization**: `FWorldInterface::WithWorld()` ensures exclusive world access
- **Packet Queue**: Thread-safe queues for cross-thread packet passing
- **Client Map**: `FMutex` protects server's client connection map

## Performance Characteristics

- **Snapshot Rate**: 10 Hz (100ms intervals) for world state synchronization
- **Heartbeat Rate**: 5 seconds for connection monitoring
- **Timeout**: 30 seconds of inactivity triggers disconnection
- **Fragmentation**: 512 byte threshold for automatic fragmentation
- **Delta Compression**: Up to 64 snapshots buffered for efficient delta transmission
- **Thread Model**: Dedicated network thread prevents blocking main game loop

## Usage Philosophy

The network architecture follows these principles:

1. **Separation of Concerns**: Base handles I/O, derived classes handle logic
2. **Thread Safety**: `FWorldInterface` prevents race conditions
3. **Event-Driven**: `EventEmitter` decouples network events from game logic
4. **Automatic Management**: Fragmentation, heartbeats, and timeouts handled transparently
5. **Scalability**: Server efficiently manages multiple clients with minimal overhead

This architecture enables robust, performant multiplayer games with minimal boilerplate code.
