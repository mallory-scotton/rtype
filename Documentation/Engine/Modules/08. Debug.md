# 🐛 Debug

## Overview

The **Debug** module provides a comprehensive runtime debugging and monitoring system for the TKD Engine, built on top of **Dear ImGui**. It offers real-time inspection and visualization of engine internals, performance metrics, network activity, input states, actor hierarchies, and configuration settings through an intuitive graphical interface.

Debug is designed to be:
- **Client-only**: Only available in client builds (`TKD_ENGINE_CLIENT`)
- **Non-intrusive**: Minimal performance impact when windows are closed
- **Comprehensive**: Covers all major engine subsystems
- **Interactive**: Live data visualization with graphs, tables, and hierarchies
- **Extensible**: Interface-based architecture allows custom debug tools

## Architecture

The Debug module is organized into **2 architectural layers**:

```
Debug/
├── Core/                          - Debug system foundation
│   ├── IDebugInterface.hpp       - Base interface for debug tools
│   └── FDebug.hpp/cpp            - Main debug menu and coordinator
│
└── Tools/                         - Specialized debug interfaces
    ├── FEngineSettingsDebug      - Engine configuration viewer
    ├── FPerformanceMonitorDebug  - FPS, frame time, memory graphs
    ├── FNetworkDebug             - Network statistics and packet inspector
    ├── FInputsDebug              - Input state and mappings monitor
    ├── FActorDebug               - Actor/class hierarchy browser
    ├── FWorldDebug               - World state and level inspector
    └── FCameraDebug              - Camera properties viewer
```

All Debug classes reside in the `tkd::debug` namespace and are only compiled in client builds. The system integrates seamlessly with the engine's rendering pipeline through ImGui integration.

## Core System

### IDebugInterface

**IDebugInterface** - Base interface that all debug tools must implement.

```cpp
namespace tkd::debug
{

#if TKD_ENGINE_CLIENT

class IDebugInterface
{
public:
    virtual ~IDebugInterface() = default;

    // Pure virtual method - must be implemented by derived classes
    virtual void Show(const FEngineSettings& settings, UWorld* world) = 0;
};

#endif

}  // namespace tkd::debug
```

**Design Pattern:**
- Pure virtual interface enforces consistent API across all debug tools
- Each tool receives engine settings and world pointer for full context
- Tools render their UI within the `Show()` method using ImGui

```cpp
// In your custom network code
void MyNetworkSystem::SendCustomPacket()

    FPacketHeader header;
    header.packetType = PACKET_TYPE_CUSTOM;
    header.sequenceNumber = GetNextSequence();
    
    std::vector<Byte> payload = SerializeCustomData();

            payload.size()
```

```cpp
{

    FMyCustomDebug m_myCustomDebug;
    bool m_showMyCustomDebug = false;

public:
    void Show(const FEngineSettings& settings, UWorld* world) override
    {
        // In main menu
        if (ImGui::BeginMenu("Debug")) {
            if (ImGui::MenuItem("My Custom Debug", nullptr, m_showMyCustomDebug)) {
                m_showMyCustomDebug = !m_showMyCustomDebug;
            }
            ImGui::EndMenu();
        }
        
        // Show window
        if (m_showMyCustomDebug) {
            m_myCustomDebug.Show(settings, world);
        }
    }
};
```

## Best Practices

### 1. Client-Only Compilation

```cpp
// GOOD: Wrap all debug code in client guard
#if TKD_ENGINE_CLIENT
    FDebug::GetInstance().Show(settings, world);
#endif

// BAD: Including debug code in server builds
FDebug::GetInstance().Show(settings, world);  // Won't compile on server
```

### 2. Minimal Performance Impact

```cpp
// GOOD: Debug windows only update when visible
if (m_showPerformanceMonitor) {
    m_performanceMonitor.Show(settings, world);
}

// BAD: Always processing debug data
m_performanceMonitor.UpdateData();  // Even when window closed
```

### 3. Use Keyboard Shortcuts

```cpp
// GOOD: Built-in shortcuts for quick access
// Ctrl+Shift+P to quickly check performance
// Ctrl+Shift+N to monitor network issues

// AVOID: Manual menu navigation during gameplay
```

### 4. Filter Debug Output

```cpp
// GOOD: Use filters in Network Debug
// Filter by packet type: "RPC" to see only RPC packets
// Toggle incoming/outgoing packets

// GOOD: Limit packet history size
static constexpr SizeT MAX_PACKET_HISTORY = 128;  // Prevent memory bloat
```

### 5. Read-Only Configuration

## Performance Considerations

### 1. ImGui Rendering Cost

**Debug UI Impact:**
- Each visible window: ~0.1-0.5ms per frame
- Closed windows: ~0.01ms per frame (just state checks)
- Complex graphs: ~0.5-1.0ms per frame

**Optimization:**
- Only render visible windows
- Limit graph history size (300 samples default)
- Use `ImGuiWindowFlags_NoResize` for static windows

### 2. Packet Logging Overhead

**Network Debug Cost:**
- Packet logging: ~50-100 microseconds per packet
- Disabled when window closed: Zero overhead
- History limit prevents unbounded memory growth

```cpp
// Efficient: Only log when debug window is active
if (m_networkDebug && m_showNetworkMonitor) {
    m_networkDebug->LogPacket(header, endpoint, isOutgoing, payload, size);
}
```

### 3. Actor/Class Hierarchy Traversal

**Actor Debug Cost:**
- Class hierarchy build: One-time on first access
- Actor list iteration: Once per frame when visible
- ~1-2ms for 1000 actors

**Optimization:**
- Use lazy evaluation
- Cache class hierarchy
- Only expand selected actors

### 4. Memory Usage

**Per Debug Tool:**
- FPerformanceMonitorDebug: ~12KB (300 samples × 2 graphs × 4 bytes)
- FNetworkDebug: ~32KB (128 packets × 256 bytes average)
- FActorDebug: ~Minimal (references existing data)
- FInputsDebug: ~Minimal (references input manager)

**Total Debug Module:**
- ~100-200KB when all windows active
- Negligible impact on game memory budget

```cpp
class FDebug

    FMyDebugTool m_myDebugTool;
```
